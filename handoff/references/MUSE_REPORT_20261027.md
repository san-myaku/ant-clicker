**L084** 問題 1

**L085** 1000匹規模まで重さを抑えたい（最優先）

**L086** 最初に試す一つ: 1-A 近傍探索の均一格子化 —— 結果を変えずに N² を消せる唯一の変更で、手間が最小、効果の上限が最も大きい。

**L087** 外挿の危険: 渋滞判定が本当に全員×全員なら、128→1000匹でその項は (1000/128)² ≒ 61倍になり、0.41ms が約25ms／ステップになる。他の項がゼロでも10倍速は不可能。逆に言えば、この項を線形化するだけで「1000匹で破綻するかどうか」が決まる。水増し計測で大半待機の条件なら2048匹でも15.3msだったことは、「動いているアリの数」が支配的である傍証になる（待機アリは安い）。

**L088** 1-A 近傍探索の均一格子化 空間ハッシュではなく「既にある格子」の再利用

**L089** 世界は96×90単位で、判定半径は体＋荷物程度（推測: 1〜2単位）に限られる。セルサイズ＝最大判定半径（例: 2単位 → 48×45＝2,160セル）にした Int32Array のセル先頭＋連結リスト（grid linked list: head[cell], next[ant]）を作り、毎ステップ冒頭に全アリを登録し直す。登録は O(N)、参照は自セル＋隣接8セルだけ。土格子（0.25単位）とは別に、アリ専用の粗い格子を持つ。

**L090** セルを跨いだときだけ登録し直す最適化は Factorio が採用した形（チャンクに「そこで終わるロボット」を登録し、仕事地点のチャンクから螺旋状に探す）と同型で、数千体規模で実証されている。

**L091** 注意: 密集した部屋では1セルに多数が入り局所的に重くなる。対策はセルサイズを判定半径ちょうどにすることと、部屋内では「渋滞判定の相手を同部屋の先行者だけに絞る」等の意味的絞り込みであり、判定を省略することではない。

**L092** Factorio 公式 Friday Facts #374（数千ロボットで全リスト走査がUPSを食うため、チャンク別リスト＋螺旋探索に変更し「数千体でも快適」） [source: https://www.factorio.com/blog/post/fff-374] https://www.factorio.com/blog/post/fff-374

**L094** 制約適合: 完全に適合

**L095** 手間 小〜中効果 大

**L096** 判定結果は「全員を調べた場合」と数学的に同一にできる（半径外は元々無関係）ので決定性を壊さない。追加メモリはセル数＋N程度。近傍数が平均10なら1000匹で候補は10⁶→10⁴、外挿25ms→約3ms弱（推測: 均一分布仮定。巣内に密集する本ゲームでは実効はこれより悪いが、N² の発散は消える）。

**L097** 1-B 部屋＋通路グラフを経路の正本にする HPA* / RimWorld region 方式 ＋ グラフ上のフローフィールド

**L098** 既に「部屋11・通路履歴点」という抽象化の素材がある。これを正式にグラフ化する: ノード＝部屋・分岐点・地表・掘削先端、エッジ＝通路区間（履歴点列への参照、長さ、幅、狭小区間フラグ付き）。経路探索は2段に分ける。

**L099** グラフ段: 部屋グラフ上の A*／Dijkstra。ノード数が1000匹規模でも部屋＋分岐で推測100〜300程度なら、全点対距離の事前計算（各ノードからDijkstra）でも現実的。掘削でグラフが変わったときだけ影響部分を再計算する。「行き先が変わるたびに再計算」は、再計算コスト自体が砂粒A*の数百分の1になるため問題でなくなる。

**L100** 局所段: 現在区間内と目的地の部屋内だけ、砂粒格子A*で体・荷物が通れるかを精緻化する（既存A*はこの範囲に縮小して再利用）。

**L101** 到達可能性: RimWorld の実例が示す通り flood-fill の領域番号一致で O(1) にでき、「到達不能なのにA*が全マップを走査して固まる」事故を根絶できる。

**L102** フローフィールドは部屋グラフ上で作る。目的地の種類は地表・女王室・餌保管・育児室・掘削前面など限られる（推測: 同時10〜20種以下）。目的地ごとに距離と次の一歩を1回計算して全員で共有すれば、グラフ段すら個別に回す必要がなくなる。ただし砂粒格子（138,240マス）で目的地別に持つと距離配列だけで約5.5MB（推測計算）になり再計算も重いので、砂粒格子では作らない。

**L103** Cities: Skylines についての正直な注記: 初代／II の公式資料で「経路を計算して保持し使い回す」方式の具体的記述は確認できなかった。むしろ II の公式 Traffic AI 説明は「経路計算はより多数・詳細になり、近傍エージェントも常時考慮する。それをマルチコアCPUの全コアで回して高速化した」と述べている。つまり同作の答えはキャッシュではなく並列化であり、単一スレッドの本ゲームには移植できない。

**L104** 副次的な小物: 砂粒A*が残る局所区間では JPS（Jump Point Search）が使える。一様コスト格子で最適性を保ちA*を1桁以上高速化し、前処理・追加メモリなし。ただし本ゲームのA*は「体と荷物がぶつからないか」を歩行ごとに判定する非一様コストなので、そのままでは適用できず、「地形だけの素通し可能性」の事前フィルタとして使うのが現実的（推測）。

**L105** RimWorld 開発者公式ブログ「Reachability at last」（領域番号による到達可能性。200×200の全再生成5.5msでも毎フレームは無理なので局所更新が必要、という率直な記述付き） [source: https://ludeon.com/blog/2013/07/reachability-at-last/] https://ludeon.com/blog/2013/07/reachability-at-last/

**L110** 制約適合: 適合（設計判断が1つ要る）

**L111** 手間 大効果 大

**L112** 完成形の型を切り抜くのではなく「実際に掘られた通路からグラフを導出する」ので方針に反しない。注意点は (a) 通路が掘り進むたびのグラフ更新を局所化すること（HPA*の既知の弱点そのもの）、(b) 局所段のA*では体・荷物の干渉を従来どおり1歩ずつ判定し続けること（グラフ段は「通れるはず」の目安にすぎず、実物の通行可否を上書きしない）。経路項0.41msの主因である長距離A*の繰り返しが消え、経路コストは匹数より目的地変更回数に比例するようになる。

**L113** 1-C 更新頻度の間引き（意思決定だけ）＋ Worker / WASM の評価

**L114** 間引けるのは意思決定だけで、移動・衝突・物理は毎ステップ必要（実物方針）。

**L115** 手空きアリの仕事探し: 全員毎ステップではなく、ステップ番号 % K == アリ番号 % K で決定的にずらす。間に仕事が発生したら、部屋単位の「未処理仕事リスト」への登録イベントで即時起床させる。

**L116** 静止中のアリ（部屋で待機し、荷物も仕事もなく、近傍に移動個体がいない）: 計画・経路の再評価を止め、起床条件（仕事登録、近傍セルの変化、女王の産卵等）をイベント化する。

**L117** 遠方判定: スマホ画面外かどうかではなく「同一区間内に他の移動個体がいるか」で決める（画面外でも渋滞は起きるため、描画都合のLODはシミュレーションに使わない）。

**L118** 決定性の条件: 間引き間隔・位相は「ステップ番号とアリ番号だけの関数」にする。実時間・乱数・描画フレームに依存させると同じ種で同じ結果にならない。設計規約として明記すべき点。

**L119** Web Worker / WASM の評価（結論: 今は採らない）: Worker は総CPUを減らさない（同じ計算を別スレッドでやるだけ）。効くのはメインスレッドの固まりと問題6の読込時の引っかかりで、10倍速の限界そのものは上がらない。毎ステップの状態往復コスト、SharedArrayBuffer に必要な COOP/COEP ヘッダと静的1ファイル配布の相性、決定性の検証範囲の拡大もあり、方針（Workerなし）にも反する。WASM（同一スレッド）は型付き配列上のタイトなループに高速化余地があるが相場は不確か（推測: 対象を絞れば数倍、全体では Amdahl で頭打ち）。全書き換え級の手間と1ファイル方針の破壊に見合わない。JS側で SoA 化・割り当て削減・ホットループの単純化を先にやる方が費用対効果が高い（一般論としての推測）。

**L120** 間引きの一般論（AI の tick rate はフレームレートと切り離せる）。ただし距離基準は本ゲームには不適で、上記の意味的基準に置き換える [source: https://reintech.io/blog/how-to-create-a-video-game-ai-with-python] https://reintech.io/blog/how-to-create-a-video-game-ai-with-python

**L127** 問題 2

**L128** 狭い通路の渋滞と、互いに待ち合う止まり

**L129** 最初に試す一つ: 2-A 区間の方向予約（単線閉塞） —— 止まりを「解消」ではなく「予防」に格上げする。ただし 2-B の検出器だけは 2-A より先に入れてよい（安く、現状把握と問題7の土台になる）。

**L130** 構造の理解が先: 巣は木（部屋＝節、通路＝辺、環はほぼない）。木の辺は「幅1〜2匹の単線区間」であり、正面衝突が起き得るのは区間内だけ、分岐の競合は節（部屋・分岐点＝広い場所）で起きる。対策も「区間の交通規則」と「節での待ち解決」に分けて考えるのが正しい。現行規則（流れの平均方向、番号タイブレーク、荷物／仕事持ち優先、細道の部分予約）は局所規則の積み重ねであり、局所規則だけでは循環待ちを原理的に排除できないことが、117匹の相互待ち例で実証されたと読むべきである。

**L131** 2-A 区間を「単線閉塞」にする 方向トークン付き区間予約（WHCA* の区間版）＋蟻の交互通行

**L132** 狭い区間（幅が2匹未満で、途中に待避できない区間）ごとに予約表を持つ: 区間は一度に一方向だけが占有でき、入口で（方向, 通過予定の隊列）を予約したアリだけが入る。逆方向のアリは区間手前の広い場所（部屋・分岐・待避所）で待つ。これは鉄道の単線閉塞そのもので、区間内に正面衝突は原理的に発生しない（検出ではなく予防）。既存の「細道は実際に狭い区間だけ予約する」を、点の予約から区間の方向予約に格上げする変更である。

**L133** 実物の蟻の裏付け: 狭い橋では流れは連続流ではなく交互の群れ（クラスタ）になる。ハキリアリ Atta colombica では幅の狭い橋で、帰還する荷物持ちを中心とする一群が渡り、出発組は橋の側に寄って待つ、という時間的組織化が観察されている。現行の「荷物か仕事を持つ方が先」は実物と一致する: Atta では出発アリが正面遭遇の80%で帰還する荷物持ちに道を譲り、荷物持ちの後ろに空荷の帰還組が付いて列を作る（荷物持ちは操縦性が低く遅いので、追い越さず付いていく方が全体では速い）。現行規則を「区間の方向は、先に区間に荷物持ちを含む隊列がいた方向を優先」「空荷は同方向の荷物持ちを追い越さない（区間内追い越し禁止）」まで拡張すると、実物の規則とほぼ一致する。

**L134** 軍隊アリ Eciton burchelli の3車線（中央＝荷物持ち帰還列、両側＝出発列）は「荷物持ちは避けない／空荷が避ける」という非対称性だけで自己組織化する。幅が2匹分ある区間ではこの非対称規則（荷物持ちは直進、空荷が壁側に寄る）で車線的秩序が期待できる。幅1匹区間では車線は作れないので閉塞管理に切り替える、という幅による使い分けが自然。

**L135** リスク（正直な注記）: 閉塞は「待ち」を増やす方向の対策でもある。長い区間を一方向にすると逆方向の待ち時間が伸び、スループットが落ちる。実物のクラスタ通行が示すように、隊列の長さに上限を設け（例: 1方向あたり最大 K 匹 or T ステップで方向を譲る。K・T は要調整の設計値＝推測）、飢餓（starvation）を防ぐ必要がある。また区間の両端に「待てる広さ」がない配置では機能しない → 問題4の待避所とセット。

**L142** 待つ場所は実物の広い床であり、アリは実際にそこに立って待つ。予約は「これから入る意思の表明」であって移動を変質させない。決定性は予約の競合解決を（到着ステップ, 優先度, 番号）の全順序で行えば保てる。予約表は区間数（推測: 数十〜数百）しかないので安い。手間の中身は区間の抽出（通路グラフ化に依存し問題1-Bと基盤を共有）、「予約した隊列が全員抜けるまで逆方向を入れない」状態機械、予約の失効条件（掘削で区間形状が変わった場合）。効果として、区間内の正面衝突とそれを起点とする相互待ち連鎖が構造的に消え、残る止まりは節での競合に限定される。

**L143** 2-B 待ちグラフの閉路検出を常時監視に 解消は Push-and-Rotate 型マクロ（実物の退避行動として）

**L144** 各アリについて「今、誰のせいで止まっているか（前の個体）」は現行実装に既にある情報である。これを待ちグラフ（Pi → Pj ＝ Pi は Pj を待つ）として保持すると、各頂点の出次数は最大1（待つ相手は最大1匹）なので、閉路検出はポインタ追跡で O(閉路長)、全体でも訪れた印を付ければ O(N) で毎ステップでも回せる安さになる。閉路を検出したら:

**L145** 閉路メンバーの中から「退くべき1匹」を全順序で決める（優先: 空荷 ＞ 仕事なし ＞ 番号大、など現行の優先観念の逆順）。

**L146** その1匹は実際に歩いて最寄りの待避先（部屋、分岐の広がり、待避所、来た道の引き返し可能な節）へ退き、閉路の他のメンバーは優先度を継承して前進する。退いたアリは区間が空いてから再合流する。これは無条件の待機解除ではなく「退避という実物の仕事」であり、禁止事項に触れない。

**L147** 優先度の継承: 待ち連鎖では「待たれている側」に後続全員の最大優先度を継承させると、連鎖の先頭が第三者に譲って連鎖が伸びる事故を防げる。原典はリアルタイム同期の Priority Inheritance / Ceiling Protocol (Sha, Rajkumar, Lehoczky 1990)。Priority Ceiling 側はデッドロック自体を防ぎ「ブロックは最大1回」という性質を持つ。FAR もデッドロックを「互いに待つユニットの cycle」として検出し局所修復で解く設計で、この検出方法自体がゲーム規模でも採用実績のある考え方である。

**L148** 前提条件の正直な評価: Push and Rotate の完全性は「頂点に1エージェント、空き頂点2つ、離散移動」の世界での話であり、体が複数マスを占め荷物で幅が変わる本ゲームにそのままでは移植できない。移植できるのは (a) 完全性の条件＝「退避できる空き場所が常にあること」という設計要件化、(b) rotate ＝ 閉路メンバー全員が一斉に1歩前進する操作（閉路が空間的にも輪になっている場合のみ可能）、(c) swap ＝ 待避所を使った入れ替え、というマクロの語彙である。保証は「閉路検出で必ず見つかる＋退避先が存在すれば必ず解ける」という形に弱まるが、それでも現行の場当たり規則より一段強い。

**L166** 3-A 「手空きは異常」という前提を捨て、予備労働力として設計する

**L167** 実物の知見: 社会性昆虫では常時50%を超えるワーカーが不活発であることが普通で、Temnothorax では平均約40%がほぼ不活発。上位20%の活発個体を取り除くと、不活発だった個体が1週間以内に活動量を上げて穴を埋める（予備労働力として実証）。逆に不活発個体を取り除いても不活発の数は回復しない＝コロニーは「活発個体の数」は維持するが「不活発個体の数」は維持しない。さらに、コロニーサイズが専門化の度合いや不活発割合を上げるわけではない（Dornhaus, Holley, Franks 2009）。

**L197** 実物の知見: 巣構造の比較研究では、大コロニーの種ほど巣が小区画化し、分岐が増え、その結果として移動距離が抑えられる。小コロニー（〜1000匹、〜10ノード以下）では巣は鎖状（チェーン）が多く、大コロニーで木状に分岐する。近道となる環状接続（shortcuts）の増加は支持されなかった (Miller et al., Evolution 2022)。木アリの採餌網では、ネットワークは総長（Steiner 木的）と経路係数（巣〜餌場距離の直線比）の妥協点にあり、分岐角の平均は約60°（種により50〜100°）(Buhl et al. 2009)。フロリダ収穫アリ Pogonomyrmex badius の巣は、1〜4本の螺旋シャフトに水平部屋が付く構成で、面積の約半分が上部1/4に偏り（top-heavy）、部屋の垂直間隔は深部ほど広がり、分岐は浅い層（<40cm）に集中する。巣は「深くしながら・部屋を増やしながら・既存部屋を広げながら」同時に成長し、サイズによらず相対形状が保たれる (Tschinkel 2004)。

**L198** 設計への翻訳:

**L199** 通路を「幹（地表〜浅層、流量大）」「枝（中層）」「末端（深層、流量小）」に階層化し、制約を層別にする: 幹では分岐間隔・出口間隔を現行（9〜14 / 2.5）より広げ＋通路幅を2匹分確保し、末端では現行値を緩めて深い部屋が開かない問題を解く。「制約を強めると深部が開けない」のは、全層一律の制約で幹の都合を末端に課しているため（解釈＝推測だが、流量階層モデルからは自然に出る）。

**L200** 分岐の置き方: 新しい部屋は「最も流量の多い既存区間」ではなく「流量に余裕のある節」から分岐させる。分岐点同士の距離はユークリッド距離ではなく区間の通過流量（過去の通過匹数で実測できる）で重み付けする。

**L201** 形状の偏り: 実物の top-heavy（浅層に面積集中）は「掘った土を地表まで運ぶ」コストと整合的で、本ゲームの運搬実物モデルとも合う。浅い層から埋める現行ヒューリスティクスは実物支持があるので維持してよい。

**L223** 問題 5

**L224** 保存形式と番号の上限

**L225** 最初に試す一つ: 5-A（番号の Uint16 化＋陣営分離）を先に、次に 5-B —— 番号空間は保存形式のスキーマそのものであり、形式を作り替えてから番号を広げると二度手間になる。

**L226** 5-A 番号空間の再設計 Uint16 化＋陣営の分離

**L227** 問題の本質: 1バイト番号の再利用（1〜128）と侵入者 200〜249 の同居は、1000匹では物理的に収まらない。運び手番号が1バイトという「参照側」の制約が本体。

**L228** 個体番号は Uint16（0 ＝ なし／未設定、1〜65534 ＝ 実個体、65535 ＝ 番外センチネル）。参照を持つ全フィールド（運び手、親、待ち先、仕事の担当者…）を一斉に Uint16 化する。コストは1参照あたり+1バイトで、1000匹×参照数個でもキロバイト級（推測計算）。

**L229** 味方と侵入者は別配列・別番号空間にし、陣営は「どちらの配列か」で表す。共通処理が必要な場面だけ（陣営1bit + 番号15bit）のタグ付き参照を使う。これで「味方が200匹を超えると衝突」は構造的に消滅する。

**L230** 部屋番号も Uint16 化（現行 Uint8Array の254上限は、部屋が増える1000匹規模では第二の壁になる）。土格子の値域（マス種別）だけは Uint8 のままでよい（種類数は増えない）。

**L231** 制約適合: 適合

**L232** 手間 中効果 上限問題の解消そのもの（先送りではない）

**L233** 開発中は旧形式互換不要という前提が効く。検証は「番号→配列の範囲内か」の境界チェックを型ごとに一元化する。手間の中身は参照箇所の洗い出しで、漏れると静かに化けるので、番号を生の数値でなく生成・検証経由に寄せる。

**L234** 5-B 保存形式を SoA バイナリ＋土の RLE にし、IndexedDB に ArrayBuffer のまま置く

**L235** 現状分析（推測を含む）: 128匹で1.2MB ということは、1匹あたり約9KB の JSON 換算であり、個体オブジェクトのキー名繰り返しと配列の数値テキストが支配的とみられる。土格子を JSON 数値配列で持てばそれだけで138,240要素 ≒ 数百KB〜1MB級になるため、現行形式のまま1000匹にすると5MB上限（後述）を確実に超える。

**L236** 個体・物体: フィールド別に型付き配列を並べる SoA（例: 位置 Uint16×2、姿勢 Uint8、状態 Uint8、荷物参照 Uint16、仕事参照 Uint16…）。1匹の固定長レコードを32〜48バイトに収めれば1000匹で32〜48KB（設計値＝推測）。

**L237** 土格子: 138,240バイトの Uint8Array をそのまま持つのではなく、行単位 RLE（同じ値の連続を [値, 長さ] で表す）。土と空気は長い連続になりやすい地形データでは RLE が劇的に効く一方、交互パターンでは膨張する、という性質が地形保存の実例で知られている。掘削前面の乱れた部分だけ生配列で持つハイブリッドも可能。

**L238** 置き場所: IndexedDB は structured clone で ArrayBuffer / 型付き配列をそのまま保存でき、非同期でメインスレッドをブロックしない。対して localStorage は同期的でメインスレッドをブロックする API であることが Mozilla の性能ベストプラクティスで明記されている。

**L239** 容量: MDN によれば Web Storage は local 5MiB + session 5MiB が origin あたりの上限。IndexedDB 等はブラウザ管理で、Safari（iOS 17以降のブラウザアプリ）でも origin あたり総ディスクの約60%が上限とされ、桁が違う。ただし Safari は「7日間操作のない origin のスクリプト作成データを削除する」追跡防止の削除があり得ることも同ページに明記されている → navigator.storage.persist() の申請と、書き出し（エクスポート）機能の併設が現実的な保険になる。

**L240** localStorage に残す場合の橋渡し: バイナリを文字列化するには Base64（+33% 膨張）が必要。Uint8Array.prototype.toBase64() / fromBase64() は2025年9月に新規利用可能となり Safari 18.2 / iOS 18.2 から対応するので、自前ループよりこれを feature detection 付きで使う。

**L289** 不変条件: 毎ステップ安く検査できるもの（荷物は必ず誰かが持つか地面にある、同一マスに体が重ならない、番号参照が範囲内、土の総量が保存される＝掘削で土は消えず運び出される、等）をアサートする。違反は即座に種とステップを残す。

**L291** 手間 小〜中効果 大

**L293** 7-B 実セーブからの分岐ファズ＋短時間多種走行

**L294** 止まりは「育った巣×特定の仕事配分」で出るので、ゼロから2時間育てるのではなく、実セーブのチェックポイント（例: ゲーム内10分ごとのスナップショット）から分岐させ、仕事割り当て・侵入者・餌出現を種で摂動した短時間走行（例: 5〜10分相当）を多数並列に回す。性質ベーステストの考え方（ランダム生成＋失敗時の最小化＝shrinking、種による再現）を使う。本ゲームではライブラリ導入より「種つきシナリオ生成器＋失敗シナリオの自動縮小（アリを間引いても再現するか試す）」を自前で持つ方が、決定的シミュレーションと相性が良い（推測）。
