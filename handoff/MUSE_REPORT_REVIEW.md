## 現物に合わせて直す点

### 近傍判定と決定性

レポートの半径1〜2、格子幅2・隣接8セルという例は推測。現行 `core.js` の判定は**移動予定点から2.6以内**。幅2なら探索範囲は最大5×5セルが必要で、常に隣接8セルだけでは相手を見落とし得る。既存案の幅3なら3×3セルでその半径を覆える。

また、ステップ冒頭だけの登録では同じステップ内に移動した個体の位置が古くなる。移動後の索引更新か、見落としがないことを示した保守的範囲が必要。元は配列の最初の該当個体を選ぶため、連結リストを逆順にたどるだけでは結果が変わる。候補の元の配列順も維持する。同室を除外する現在の規則も勝手に変えない。

「同じ結果が再現する」と「修正前と同じ行動をする」は別。仕事探しを番号ごとにずらす案は決定的でも行動時刻を変える。既存ログではゴミ一覧を最初に問う時点の変更が幼虫の成長を変えた例もあり、純粋な最適化としては扱わない。

### 交通と止まりの検出

方向予約は狭い区間内の正面進入を防ぐ案として評価する。**巣全体の停止がなくなる保証ではない。** 隣接区間を互いに待つ、出口が埋まる、一方向の列が終わらず逆方向が入れない、といった条件も検証する。既存の二列通れる幹線を単線へ変えない。予約を解くために区間内の個体を消したり、空き場所へ飛ばしたりしない。

監視では `waitingFor` だけでなく、実際の `yieldHold`・区間予約・仕事/荷の待ち理由も区別する。正常な休息、産卵待ち、給餌間隔、保管満杯を無進行異常にしない。検出は状態を変えず、直前の完全保存・操作履歴・ソースhash・ステップ・関係個体を残す。種とステップだけではユーザーの操作を再現できない。

「同じマスに2匹いる」を一律に不正とするアサートも追加しない。現行は連続座標で、個体同士の通行と地形/荷の掃引は異なる規則を持つ。検査が正しい挙動を禁止しないよう、先に条件を定義する。

### 保存は一部がすでに圧縮済み

土・部屋タグ・掘削予定の粒配列は `encodeGrains()` の **rle8**、物体は **bodies50le** のバイナリをBase64化している。「土がそのままJSON数値配列だから、まずRLEへ」という前提は当てはまらない。ただし粗い地形/交通配列や個体の経路/履歴などJSONのままの部分も残る。

今回、同梱の128匹の検証保存 `qa/world-scale.json` を解析した。6816ゲーム秒の固定保存で、前回の新規通し6754秒の保存や実ユーザーのセーブとは別。ファイルは変更していない。

| 内訳 | UTF-8バイト数 |
| --- | ---: |
| 保存全体 | 1,216,687 |
| 個体配列全体 | 899,461 |
| 個体の歩行履歴 trail の値の合計 | 777,730 |
| 個体の現在の path の値の合計 | 82,757 |
| 掘削仕事全体 | 108,433 |
| 物体データ全体 | 60,638 |
| 土のRLE | 28,409 |

値の内訳は `Buffer.byteLength(JSON.stringify(value),'utf8')` で、項目名/外側の区切りを含まない。歩行履歴だけで全体の約64%、11,726点。したがって、まず履歴・経路・仕事に含まれる姿勢列を、必要な状態を保ったまま表現し直せるか調べる価値がある。`trail` は退避に必要で、単なるログとして削除しない。

測定の入力hashと内訳は [保存の内訳](references/MUSE_SAVE_SIZE_20261027.json)。これだけで1000匹時の容量や速度を保証しない。自動復旧用の複製も含めて容量を測る。

位置をUint16、角度をUint8へ単に詰め替えると、現在の連続座標/回転の精度を落とし、保存復元の完全一致や身体/荷の通過条件を壊し得る。まずFloat64相当の精度を維持する。番号のUint16は有効な選択肢だが、前案のUint32も維持できる。運び手欄だけなら908物体で差は1,816バイト（レコード配置やBase64は別）。番号の幅を保存肥大の主因として扱わない。

IndexedDBは非同期ストレージとして候補になるが、形式変更・復旧・書き出し・厳密検査の設計と分けて評価する。移行すれば全復元処理が自動で軽くなるわけではない。

### 増殖・巣の形はゲーム設計として検討する

現行の産卵も無条件ではなく、保管餌2個以上・育児中の数・人口上限で制限される。育児中は最大20という別の制限があり、産卵間隔だけを短縮しても足りない。

女王への実際の世話や食料の供給で産卵を支える案は、仕事の需要と成長を結ぶ候補。ただし特定種の実験結果を全アリ共通の必須条件にしない。大型幼虫を必須にすると、幼虫を失った後に再開できなくなる恐れがある。基礎産卵・初期女王室・襲撃後の回復も含めて設計する。40→20→10→5秒は従来案の仮値であり、今回採用した値ではない。

休息をすべて不具合にせず、需要があるのに動けない個体と、正常に休む予備個体を分ける。稼働率30〜50%を達成するための飾り仕事は作らない。ユーザーの役割配分を需要駆動へ置き換える案も、別の操作設計として未採用。

また「深い部屋が開けない」は過去の規則変更での失敗で、現行は深い2室を開く通し確認に合格済み。流量階層化はその未修正バグへの即効薬ではなく、今後の大人口への設計候補とする。待避場所を作る場合も、実需要に応じて本人が掘って搬出する。

### 出典と制約の扱い

- Factorio公式のチャンク索引は、仕事を渡す相手を探す工夫の実例。蟻の近傍判定にも活用できる発想だが、同じ倍率が出る証拠ではない。[公式記事](https://www.factorio.com/blog/post/fff-374)
- RimWorldの領域番号は到達不能探索を避ける実例。ただし本作で単純な空洞のつながりが一致しても、身体・荷・旋回が通る保証にはならない。[開発者記事](https://ludeon.com/blog/2013/07/reachability-at-last/)
- Cities II公式記事はマルチコア活用を説明しているが、キャッシュの有無は記述から断定できない。Museの「キャッシュではなく並列化」は言い過ぎ。今回の経路共有案は本作の実空洞から設計する。[公式記事](https://www.paradoxinteractive.com/games/cities-skylines-ii/features/traffic-ai)
- 不活発個体が予備として動く実験はあるが、特定種/実験条件の結果で、ゲームの稼働率の正解を定めるものではない。[PLOS ONE原著](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0184074)
- 女王の継続的産卵と随伴ワーカー数の関係も原著で確認できる。本作への導入条件や倍率は別の設計判断。[Laskis & Tschinkel原著](https://academic.oup.com/jinsectscience/article/9/1/2/889276)
- IndexedDBは非同期でオブジェクトやバイナリを保存できる。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

レポートの「Workerなし」「1ファイル」は提示された評価条件。ユーザーがMuseへ別途渡した制約かは未確認で、現行は複数ファイル。恒久的な禁止と勝手に確定しない。今回は格子化/経路共有を先にするため、この未確認点で作業が止まるわけではない。

Worker/WASM/SoA/全点対距離表を一度に導入しない。後回しの理由は、本作で先に計算量/必要状態を整理して測るためであり、単一ファイルでは技術的に不可能と断定したためではない。

## 改訂候補の順序

1. 実行条件を分けた計測と、読み取り専用の止まり検出を整える。前回の並列browser速度条件1件は未解決のまま。レポートはこの試験を検証していない。
2. 近傍格子化で行動が変わらないことを確認する。
3. 実空洞の経路共有を進め、狭い区間の予約/待避を小規模ケースで検証する。
4. 番号/保存・研究・産卵/育児の設計を合わせ、256/512/1000匹で実際の成長・運搬・衛生・交通を確認する。

読込の段階別時間、1000匹の実動作性能、変更後の圧縮率・成長テンポは未測定。今回実行したのは固定保存のサイズ解析だけ。全検証や実機Safariを再実行したことにはしない。ゲーム・生成器・保存・UIは未変更。
